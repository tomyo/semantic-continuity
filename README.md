# Web Progressive Materialization (WPM)

> A browser-aligned architecture for composing, materializing, and progressively enhancing HTML documents without requiring a framework or mandatory build step.
>
> _Toward a simpler, saner, more joyful web._

## Overview

Web Progressive Materialization explores an alternative direction for web architecture where:

- HTML remains the canonical source of truth
- Documents are valid and meaningful before enhancement
- Composition can happen at build time, edge time, or runtime
- Progressive enhancement is optional but powerful
- The same composition semantics work across environments
- The final output remains clean, portable HTML

The goal is not to replace the web platform with another application runtime, but to define minimal document-level primitives that align with existing web standards and browser behavior.

## Core Principles

### 1. HTML First
Every document must remain valid HTML before and after enhancement. A page should open directly in the browser, remain meaningful without JavaScript, and remain inspectable, archivable, and portable. HTML is not treated as disposable output generated by an application runtime. It is both the source and the durable materialized state.

### 2. Enhancement Is Optional
Enhancement improves UX, responsiveness, navigation, interactivity, freshness, streaming, and progressive loading. But enhancement should never become the sole source of meaning. If JavaScript fails, or if runtime enhancement fails partially, the document should still function.

### 3. Composition Is Environment-Agnostic
The same composition semantics should work consistently in static builds, edge rendering, local development, browser runtime materialization, and offline environments. Composition primitives should remain pure, deterministic, and portable. This allows the same document to progressively converge toward equivalent structure regardless of where composition occurs.

### 4. Deterministic Progressive Convergence
Different environments may contribute to materialization (build systems, edge runtimes, browser runtimes). But all paths should converge toward semantically equivalent HTML. The browser runtime is not a separate application reality; it is another participant in document materialization.

### 5. Browser-Aligned Architecture
The architecture intentionally builds on top of native HTML semantics, browser parsing rules, progressive enhancement, web components lifecycle, standard DOM behavior, and streaming-compatible HTML. The goal is to complement the platform rather than abstract it away.

## Resolution Semantics

### Documents Are Always Resolved
"Unresolved" does not mean unusable. A document may still be progressively enhanced, refreshed, upgraded, rematerialized, streamed, or incrementally improved. But the baseline document remains valid and meaningful. This differs from architectures where the client runtime is responsible for constructing the entire application state from scratch.

### Runtime Upgrades
Runtime logic should focus on upgrading, refreshing, resolving latent regions, and enhancing UX—not replacing the entire document. Examples include refreshing stale regions, progressively loading content, attaching behaviors, enhancing navigation, and replacing placeholders with fresher materialized content.

### Semantic Equivalence
Client-side reconstruction should converge toward the same semantic structure as server-rendered output, static builds, and edge-rendered output. This avoids divergence between environments and preserves inspectability and portability.

## Composition Model

### Region Ownership & Slots
A region owns its subtree, its enhancement lifecycle, and its rematerialization behavior. Ownership boundaries should remain explicit and stable. Slots provide explicit composition boundaries between regions. Instead of implicit inheritance or hidden rendering hierarchies, composition should happen through clearly declared insertion points.

### Declarative Composition & Semantic Parts
Composition metadata should remain declarative and HTML-aligned (e.g., layouts, slots, placeholders, fragments). The architecture avoids introducing a separate templating language or reactive DSL. Instead, we use standard attributes like `part` as a **semantic addressing mechanism** for rendering, querying, and styling.

Instead of string interpolation (`{{ title }}`) or framework mapping (`className="..."`), we use:

```html
<article>
  <h2 part="title"></h2>
  <div part="content"></div>
</article>
```

- **CSS targets parts:** `[part="title"]` (Light DOM) or `::part(title)` (Shadow DOM).
- **JS targets parts:** `element.querySelector('[part="title"]')`.
- **Renderers target parts:** A minimal server/client function populates the parts instead of parsing template strings.

### Stateless DOM Transformers
Components should mostly act as stateless DOM transformers. Rather than maintaining a parallel state object in JavaScript, the DOM itself acts as the source of truth. To keep components lightweight, predictable, and memory-efficient:
- **Use HTML state as the source of truth:** Store data in attributes (`data-*`, `aria-*`), native properties, and standard DOM state.
- **Rely heavily on event delegation:** Catch events higher up the DOM tree instead of binding to individual elements.
- **Minimize instance listeners:** Avoid binding multiple specific event listeners per component instance.
- **Avoid subscriptions:** Steer clear of complex reactive pub/sub models or observable streams tied to component lifecycles.
- **Avoid timers:** Limit the use of `setTimeout` and `setInterval` to prevent memory leaks and synchronization issues.

## URL & Resource Semantics

### Referential Stability
A core principle of WPM is that **materialization should preserve referential stability**. A fragment must behave the same way regardless of where it is composed.

To ensure reusable fragments do not become awkward, we conceptually differentiate how URLs are typed and resolved:

| URL Type | Resolved Relative To |
|---|---|
| **Assets** (images, styles) | Source file |
| **Imports** (scripts, modules) | Source file |
| **Fetch endpoints** | Source file |
| **Navigation** (links) | Materialized document |
| **Canonical URLs** | Materialized document |

### URL Resolution Rules
To create deterministic behavior without overengineering, WPM adopts the following resolution semantics:
1. Relative resource references resolve against the originating document.
2. Composition does not alter authored resource meaning.
3. Materialization may normalize URLs to canonical form.
4. Navigation semantics resolve against the final document context unless explicitly scoped.
5. Serialization strategy is independent from composition semantics.

### Recommendations for Large Systems
To keep components decoupled and maintainable:
- **Prefer:** Root-relative URLs, import-map aliases, and explicit base conventions.
- **Avoid:** Deep relative chains (e.g., `../../../`), which quickly become architectural debt.

### Materialization and `<base>`
While you should avoid relying on `<base>` to manage arbitrary, fragmented architectures (because it globally mutates resolution and creates composition conflicts), it becomes very powerful when used in a coherent, materialized document. 
Because the final document is the authority, `<base>` can be used efficiently by the materializer to anchor the finalized, deterministic paths.

## URL & Resource Lifecycle (The Architecture)

This approach creates an elegant distinction between the authoring experience and the runtime reality.

**1. Authoring Phase (Filesystem-Relative)**
Developers use normal, local file-relative semantics (`import "./utils.js"`, `<link href="./card.html">`). 
This preserves locality, composability, refactoring ease, and portability. It aligns with standard developer intuition (like ES modules).

**2. Composition Phase (Provenance-Aware)**
The composition unit or materializer tracks provenance (the source URL, resolution context, and dependencies) as temporary internal state. Provenance exists strictly as a composition-time concern, not a permanent runtime abstraction.

**3. Materialization Phase (Normalized)**
All URLs are resolved into final, coherent document semantics. Depending on the deployment strategy, paths might be rebased, canonicalized, made absolute, or root-relative. The materializer resolves the original provenance into these stable document semantics.

**4. Runtime Phase (Final Document Semantics)**
The browser receives one coherent document. There is no hidden provenance layer, no fragmented URL resolution contexts, and no framework-like indirection. Standard platform URL semantics apply. 

### A Core Principle for URLs
**Composition units have source identity during resolution, but materialized documents expose coherent document identity.**

This prevents the runtime complexity of trying to maintain "fragment provenance" indefinitely within the DOM, while maintaining perfect authoring ergonomics.

### Long-Term Direction
Eventually, this model aligns naturally with:
- HTML Modules
- Scoped resource graphs
- Import maps
- Package-style document systems
- Edge-native dependency graphs

This is the healthiest direction because it builds on top of the web without inventing a parallel ecosystem.

## Materialization Layers

1. **Canonical HTML:** The base document. Valid, meaningful, navigable, portable.
2. **Composition Metadata:** Additional structure describing layouts, ownership, boundaries, and progressive regions. This metadata should not invalidate the document.
3. **Runtime Enhancement:** Optional upgrades that improve UX and interactivity while preserving semantic equivalence with the canonical document.

### Component Categories
Based on these layers, a component does not require JavaScript to exist. Components are structural first, behavioral second:
- **Structural Components:** Pure HTML structure. No JS required (e.g., `<site-header>`, `<article-preview>`). They provide composition, semantics, styling boundaries, and AI readability.
- **Enhanced Components:** HTML-first structure with optional behavior. They use JS to enhance the existing materialized HTML (e.g., `<image-carousel>`, `<share-button>`).
- **Autonomous Components:** Runtime-owned UI for highly dynamic client-side features (e.g., `<live-chat>`, `<search-overlay>`).

## Development Model

The same project should support multiple modes naturally:

| Mode | Behavior |
|---|---|
| **Static HTML** | Works directly in the browser |
| **Local Development** | Runtime materializes missing regions |
| **Build Step** | Outputs fully materialized HTML |
| **Edge Runtime** | Materializes on request |
| **Offline Saved Page** | Still meaningful |

This symmetry reduces the distinction between development, deployment, and runtime environments.

## Ecosystem & Direction

**Relationship To Existing Ecosystems:**
This architecture is intentionally compatible with progressive enhancement, server-driven HTML, web components, htmx-style interaction models, edge-native rendering, and static-first architectures. It is *not* intended to replace the web with a virtual DOM runtime, a mandatory hydration model, or a client-owned application tree.

**Non-Goals:**
This project is currently not focused on creating a frontend framework, inventing a new templating language, replacing browser semantics, introducing a custom reactive runtime, or enforcing a specific rendering pipeline. The focus is on defining interoperable document-level semantics and materialization principles.

**Direction:**
Web Progressive Materialization explores a web architecture where HTML remains durable, enhancement remains optional, composition remains deterministic, runtime remains lightweight, documents remain inspectable, materialization remains progressive, and browser semantics remain central. The long-term goal is not framework dependency, but resilient and interoperable web-native systems.
